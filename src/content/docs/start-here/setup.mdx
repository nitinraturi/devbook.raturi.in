The [setup prompt](/#setup) does all of this for you. The steps below show the same setup done by hand. New to instruction files? Read [How Devbook works](/start-here/how-it-works/) first.

**You need:** a git repository, and an assistant that reads `AGENTS.md` or `CLAUDE.md`, such as Claude Code or GitHub Copilot in agent mode, with file editing and terminal access turned on.

## 1. Choose how to add Devbook

Both methods put the files in `.devbook/`, so the rest of the setup is the same. Each release is a dated git tag, such as `v2026.11.02` (`v2026.11.02.1` for a second release that day). Pinning a tag means Devbook changes only when you move to a newer one. Pick a tab.

<Tabs syncKey="method">
<TabItem label="Submodule (tracks updates)">

Pins the newest release. You update with a few git commands, and every update shows up as a reviewable change.

```sh
TAG=$(git ls-remote --tags --refs --sort=-version:refname https://github.com/nitinraturi/devbook.raturi.in 'v*' | head -n1 | cut -d/ -f3)
git submodule add https://github.com/nitinraturi/devbook.raturi.in .devbook && git -C .devbook checkout -q $TAG && git add .devbook
```

To get every change as soon as it lands instead, follow `main`: `git submodule add -b main https://github.com/nitinraturi/devbook.raturi.in .devbook`.

</TabItem>
<TabItem label="Copy (plain files)">

Downloads the newest release as plain files that you commit, and records its tag in `.devbook/VERSION`. It works offline afterwards, needs no submodule support from tools or cloud agents, and only changes when you download again.

```sh
REF=$(git ls-remote --tags --refs --sort=-version:refname https://github.com/nitinraturi/devbook.raturi.in 'v*' | head -n1 | cut -d/ -f3) && P=devbook.raturi.in-${REF#v} && rm -rf .devbook && mkdir -p .devbook && curl -fsSL https://codeload.github.com/nitinraturi/devbook.raturi.in/tar.gz/$REF | tar -xz --strip-components=1 -C .devbook $P/instructions $P/stacks $P/templates $P/skills $P/kit $P/LICENSE-CC-BY-4.0 && echo $REF > .devbook/VERSION
```

To download a particular release, or `main` for the latest changes, start with `REF=v2026.11.02` or `REF=main` instead of the `git ls-remote` part.

On Windows PowerShell, which has no `rm -rf` or `mkdir -p`, use the `curl.exe` and `tar.exe` that ship with Windows 10 and later:

```powershell
$ref = (git ls-remote --tags --refs --sort=-version:refname https://github.com/nitinraturi/devbook.raturi.in 'v*' | Select-Object -First 1) -replace '.*/', ''; $p = "devbook.raturi.in-$($ref -replace '^v', '')"; Remove-Item -Recurse -Force .devbook -ErrorAction SilentlyContinue; New-Item -ItemType Directory -Path .devbook | Out-Null; curl.exe -fsSL "https://codeload.github.com/nitinraturi/devbook.raturi.in/tar.gz/$ref" -o devbook.tar.gz; tar.exe -xzf devbook.tar.gz --strip-components=1 -C .devbook "$p/instructions" "$p/stacks" "$p/templates" "$p/skills" "$p/kit" "$p/LICENSE-CC-BY-4.0"; Set-Content .devbook/VERSION $ref; Remove-Item devbook.tar.gz
```

Without a terminal, open the [list of releases](https://github.com/nitinraturi/devbook.raturi.in/tags) and download the ZIP of the newest tag. Copy its `instructions/`, `stacks/`, `templates/`, `skills/` and `kit/` folders and its `LICENSE-CC-BY-4.0` file into `.devbook/`, and write the tag name in `.devbook/VERSION`.

</TabItem>
</Tabs>

## 2. Connect your assistants

<Steps>

1. Create `AGENTS.md` at the repository root and fill in the Project section with your real commands, layout and rules. In the Devbook section, keep the three `@` lines and only the "read" lines that apply: see [the table of when to load each file](/start-here/how-it-works/#mandatory-and-optional-files), plus one stack note for each technology you use.

   <Code code={agentsTemplate} lang="md" title="AGENTS.md" />

2. Create `CLAUDE.md` containing one line:

   ```md
   @AGENTS.md
   ```

3. Create `.github/copilot-instructions.md`:

   <Code code={copilotTemplate} lang="md" title=".github/copilot-instructions.md" />

4. Link each path-scoped file you chose (design, api-data, database, seo, content, mobile) into both rule folders. Claude Code then loads it only when a matching file is read or edited, and Copilot when one is edited:

   ```sh
   mkdir -p .claude/rules .github/instructions
   ln -s ../../.devbook/instructions/design.md .claude/rules/devbook-design.md
   ln -s ../../.devbook/instructions/design.md .github/instructions/devbook-design.instructions.md
   ```

5. Link the skills that fit, so the assistant can load them for matching tasks. `devbook-security-review`, `devbook-release-check` and `devbook-upgrade` suit every project; add `devbook-feature-doc`, `devbook-api-endpoint`, `devbook-db-migration` or `devbook-seo-audit` with their instruction files:

   ```sh
   mkdir -p .claude/skills
   ln -s ../../.devbook/skills/devbook-security-review .claude/skills/devbook-security-review
   ```

6. Commit `.devbook` (plus `.gitmodules` for a submodule), `AGENTS.md`, `CLAUDE.md`, `.github/copilot-instructions.md`, `.claude/rules/`, `.claude/skills/` and `.github/instructions/`, then start a new chat.

</Steps>

## 3. Optional: add the enforcement kit

Instructions are context, so an assistant can still miss a rule. The kit in `.devbook/kit/` turns a few of them into checks that tools run. The setup prompt asks before installing any part, and you can add it later:

- **Claude Code hooks** that block `git push`, `.env` edits and recursive `rm` outside the project, and say when a newer Devbook release exists.
- **Git hooks** that scan staged changes for secrets with gitleaks and check commit messages.
- **Starter CI** for GitHub Actions, for Node.js or Python, with every action pinned to a commit SHA.

[Use the enforcement kit](/start-here/enforcement-kit/) has the install steps, what a block looks like and the limits. The kit is MIT-0, so you can copy and change it without credit.

## How the instructions load

Core, security and testing load in every chat through the `@` lines; Claude Code expands them, and Copilot, Codex and Cursor are asked to open them. The path-scoped files load when a matching file is read or edited (Claude Code) or edited (Copilot), and every assistant can open the files in the "read" list when a task calls for them. Skills load only their name and description until a task needs them. [How Devbook works](/start-here/how-it-works/#how-each-assistant-loads-the-rules) explains each assistant and which rule wins.

To load everything in every chat instead, for example in a short-lived project where cost doesn't matter, replace the "read" lines with `@` lines (`@.devbook/instructions/design.md`) and skip the links. Write `@` paths as plain text, because an `@` path inside backticks is not imported.

<Aside type="caution" title="Symlinks, cloud agents and submodules">
On Windows, symlinks need Developer Mode and `git config core.symlinks true`; without them, skip steps 4 and 5 and rely on the "read" lines. Hosted agents only see a submodule's files if their checkout includes submodules. If an agent says the files are missing, add `git submodule update --init` to its setup steps. For the Copilot coding agent, those steps live in `.github/workflows/copilot-setup-steps.yml`. You can also switch to the Copy method, whose files are in the repository itself.
</Aside>

## Update, clone or remove

Before you update, read the [changelog](https://github.com/nitinraturi/devbook.raturi.in/blob/main/CHANGELOG.md) entries added since your version. Entries with an **Upgrade** note need a change in your project, such as a new line in `AGENTS.md` or a new link.

<Tabs syncKey="method">
<TabItem label="Submodule (tracks updates)">

```sh
git -C .devbook describe --tags                                # the version you use
git -C .devbook fetch --tags                                   # fetch new releases
git -C .devbook tag -l 'v*' --sort=-version:refname | head -n5 # list the newest
git -C .devbook diff HEAD v2026.12.01 -- CHANGELOG.md          # what changed up to that release
git -C .devbook checkout -q v2026.12.01 && git add .devbook    # move to it, then commit
git clone --recurse-submodules <your-repo>                     # clone a project that uses Devbook
git submodule update --init                                    # fetch .devbook in an existing clone
git rm .devbook                                                # remove; then delete the Devbook section and links
```

If you follow `main`, update with `git submodule update --remote .devbook` instead. To pin a submodule that follows `main`, run `git config -f .gitmodules --unset submodule..devbook.branch`, then check out a tag as above.

</TabItem>
<TabItem label="Copy (plain files)">

`.devbook/VERSION` shows the version you use. Run the download command again, then review `git diff .devbook` and commit. The command replaces the whole folder, so files removed upstream are removed in your copy too. To remove Devbook, delete `.devbook/`, the Devbook section of `AGENTS.md` and the `devbook-*` links in `.claude/` and `.github/instructions/`.

To switch from Copy to Submodule, delete `.devbook/`, commit the deletion, then run the submodule command.

</TabItem>
</Tabs>

Either way, your repository records exactly which Devbook text it uses, so an update is a normal reviewable change. Review it before you commit: these files steer your assistant, so treat an update like a dependency upgrade. If a release doesn't suit your project yet, stay on the previous tag.
